# Angle C: Prompt-Injection Defences, Detectors, and Benchmarks — Literature Map

Survey date: 2026-09-08. All 29 arXiv entries below were verified against the live arXiv record
(export API or arxiv.org/abs page); abstracts were fetched, not recalled from memory.
"Pipeline position" states where each work assumes the defence/benchmark sits in a
document pipeline (image -> OCR -> text -> LLM), which is the axis our paper measures.

## Non-arXiv landscape items (verified via web, no arXiv record)

- **OWASP LLM01:2025 Prompt Injection** (genai.owasp.org): canonical industry framing; recommended mitigations (input filtering, privilege separation, human-in-the-loop) are described at the text/application layer; OCR appears only implicitly under "multimodal injection" as a risk, with no placement guidance.
- **Meta Prompt Guard / Prompt Guard 2** (model card, 2024-25): 86M/276M-parameter classifier for injections/jailbreaks; operates strictly on **text strings** handed to it — anything upstream (OCR, PDF extraction) is out of scope by construction.
- **ProtectAI DeBERTa-v3 injection detector, LLM-Guard** (HF/model cards): same contract — text in, verdict out.
- Industry blog posts (2026: TianPan.co, Cloud Security Alliance, C. Schneider) discuss "OCR-based screening" and "format normalization" (render document, re-OCR it to discard hidden layers) as *proposed* mitigations for document/multimodal injection — but these are informal recommendations, not evaluated papers.

## Notes: where defences sit (mapping to our filter-placement question)

1. **Model-internal / training-time** (no explicit filter): StruQ, SecAlign, Instruction Hierarchy, Jatmo, BIPIA's fine-tuning defense. Input is assumed to already be text; conversion stages invisible.
2. **Prompt-assembly transforms**: Spotlighting (delimiters/datamarking/encoding), BIPIA border strings, prompt sandwiching (AgentDojo baselines). These necessarily run **after** text exists, i.e., post-OCR, but no paper varies the transform's position relative to a conversion stage.
3. **Text-in classifiers/sanitizers**: PromptGuard-class guards, InjecGuard, PromptShield, DataSentinel, PromptArmor, Attention Tracker, PIShield. All define their input as a text string; none consider that the string may be an OCR artifact or test detection pre- vs post-conversion.
4. **Agent-runtime / system-level**: CaMeL, MELON, Task Shield, RobustRAG, design patterns, Prompt Injection 2.0. Placement is relative to tool calls and dataflow, not modality conversion.
5. **Benchmarks**: BIPIA, InjecAgent, AgentDojo, ASB, LLMail-Inject, PromptShield-bench, NotInject, Liu et al. — every injection channel is textual (emails, web pages, tool JSON, passages). None contains an image->OCR->text stage, so filter placement around OCR is untestable in all of them.
6. **Multimodal attack papers** (2307.10490, 2408.03554, 2603.03637) establish that injections can enter *before* any text exists — via adversarial embeddings or rendered text read by implicit OCR — but their defense treatment is limited to a system-prompt instruction (GHVPI, ASR 15.8%->1.8%) or a call for future work.

**Gap our paper fills:** no verified paper or benchmark evaluates *where* a filter should sit relative to an OCR/modality-conversion stage (pre-OCR image screening vs post-OCR text filtering vs both). The closest artifacts are informal industry suggestions (re-render + re-OCR normalization) and the multimodal attack papers' observation that text-only defenses miss image-borne payloads. The entire defense literature's implicit contract is "input is already text."
